# Optima Platform — контракт для будущего бэкенда

Версия документа: 2026-10-17 · Состояние: frontend-first, API для интеграции **не подключён**.

## Предметная модель

- **Company** (`id`, `inn`, `name`, `members`, `roles`): покупатель. Для поставщика отдельная модель `Supplier` и проверка реквизитов.
- **Need** (`id`, `companyId`, `title`, `quantity`, `unit`, `deadline`, `status`): спрос компании. Не является заявкой поставщику.
- **Procurement** (`id`, `buyerId`, `supplierId`, `sku`, `quantity`, `collectedQty`, `thresholdQty`, `singlePriceKop`, `groupPriceKop`, `deliveryKop`, `delivery`, `status`): конкретная закупка. Объём группы — агрегированный показатель, договор и платежи **индивидуальны**.
- **Question** (`id`, `procurementId`, `author`, `proposal`, `proposedDelivery`, `status`, `answeredAt`): предварительное предложение, **не имеет эффекта изменения контракта**.
- **Contract** (`id`, `number`, `purchaseId`, `version`, `kind`, `status`, `amountKop`, `proposedDelivery`, `confirmedAt`): отдельный документ, который требует подтверждения. Изменение в вопросе порождает новый проект документа.
- **PurchaseTransfer** (`id`, `procurementId`, `reference`, `sumKop`, `status`, `date`): платёж, относящийся к закупке Optima. **Не банковская выписка**.
- **SupplierOffer** (`id`, `supplierId`, `title`, `thresholdQty`, `collectedQty`, `groupPriceKop`, `singlePriceKop`, `promoted`, `published`): предложение поставщика.

Суммы — **целые копейки**. Время в API — RFC 3339 UTC, отображение — локализованное. Все демосуммы и даты на текущем фронте вымышлены.

## API v1

Настройка клиента: тег `<meta name="optima-api" content="https://your-api.example">` включает HTTP-адаптер вместо localStorage (в демо атрибут отсутствует). Все mutation-методы **возвращают обновлённый snapshot** того же формата, что `GET /api/v1/buyer/workspace`; для production лучше внедрить нормализованные DTO, статусную машину и инвалидировать кэш после записи.

| Метод | URL | Назначение |
|---|---|---|
| GET | `/api/v1/buyer/workspace` | Снимок данных текущей компании-покупателя |
| GET | `/api/v1/supplier/workspace` | Только собственные предложения, обращения и данные поставщика |
| POST | `/api/v1/questions/{id}/answer` | `{ "decision": "accept"\|"decline" }` — только предварительный ответ |
| POST | `/api/v1/contracts/{id}/confirm` | `{ "acknowledged": true }` — в демо подтверждение; ЭП/ЭДО отдельно |
| POST | `/api/v1/contracts/{id}/decline` | Отклонить неподтверждённый документ |
| POST | `/api/v1/needs` | Создать потребность |
| DELETE | `/api/v1/needs/{id}` | Удалить потребность |
| POST | `/api/v1/notifications/read` | `{ "id": "NT-20" }` или `{ "id": "all" }` |
| PATCH | `/api/v1/buyer/settings` | Обновить профиль организации |
| POST | `/api/v1/supplier/offers` | Опубликовать предложение поставщика |
| POST | `/api/v1/supplier/offers/{id}/promotion` | В демо — сменить флаг продвижения (не оплата) |

## Обязательные инварианты бэкенда

1. Ответ в «Вопросах» **не обновляет** дату, цену, количество и остальные поля действующего контракта. При предварительном согласии создаётся отдельная версия будущих условий со статусом `review`.
2. Подтверждение версии документа выполняется только уполномоченным пользователем. На сервере: RBAC, проверка прав на конкретную компанию, optimistic locking через `version`/`If-Match`, журнал событий, защита от повторной операции через `Idempotency-Key`.
3. Действительное подписание требует отдельного юридического процесса с ЭДО / УКЭП. Кнопка `confirm` во фронтовом демо **не считается электронной подписью**.
4. `PurchaseTransfer` должен приходить от доверенного источника после банковского согласия/авторизации. Фронт **не запрашивает** реальные переводы компании.
5. Поставщик видит только **свои** предложения, обращения и документы. Нельзя раскрывать закупки и контакты других поставщиков (tenant isolation).
6. Продвижение поставщиков должно маркироваться как реклама и учитываться отдельно от алгоритма сопоставления спроса. В текущей версии деньги за продвижение **не списываются**.
7. Каждый статусный переход подтверждается сервером и логируется. Сервер — источник истины для `collectedQty`, тарифов, документов, платежей и срока поставки.

## Авторизация и инфраструктура

Предлагается OAuth2/OIDC через доступный корпоративный провайдер, HTTP-only secure cookies, CSRF защита, RBAC (buyer admin, buyer editor, buyer viewer, supplier admin, supplier editor), server-side авторизация каждой операции. Отдельные интерфейсы: `dist/workspace` (покупатель, адаптивный веб), `dist/supplier` (поставщик, ПК). Общая доменная модель в `dist/workspace/model.js`, исходные демоданные в `seed.js`, HTTP seam в `api.js`. Нативное мобильное приложение — позже на том же API, здесь уже подготовлен адаптивный веб.

## Приёмочный сквозной сценарий

Покупатель получает вопрос о переносе воды с 21 на 22 октября. Предварительное согласие **не меняет** закупку; появляется проект версии контракта. Только отдельное демоподтверждение меняет плановую дату и переводит закупку в исполнение. Серверная версия обязана воспроизвести этот сценарий с RBAC, версиями документа и аудитом.
